    1. Descripción de temas aprendidos con mis propias palabras

    (Tecnología web backend, arquitectura cliente-servidor, servidores web, PHP y JSP, ciclo de vida y despliegue)

    Backend web y arquitectura cliente-servidor

    El backend es la parte de una aplicación web que corre en el servidor: recibe los datos del formulario, los valida, usa la sesión y arma la respuesta que se devuelve al navegador. En la arquitectura cliente-servidor el navegador (cliente) envía una petición a un puerto donde escucha un servidor, y el servidor responde con un código de estado, cabeceras y un cuerpo, normalmente HTML.

    El recorrido completo de una petición es: cliente → DNS → TCP/IP → petición HTTP → servidor web → backend (PHP o JSP) → respuesta HTTP → renderizado en el navegador. En local, localhost se resuelve a 127.0.0.1 y el servidor atiende en el puerto que se configuró.

    Ciclo solicitud-respuesta HTTP y códigos de estado

    HTTP no guarda estado: cada petición es independiente y para recordar al usuario se usa una sesión identificada por una cookie (PHPSESSID en PHP y JSESSIONID en JSP). Los códigos de estado indican qué pasó con la petición.

    Códigos de estado usados en la práctica

    PHP: ciclo de vida, superglobales y sesiones

    En PHP cada petición ejecuta el script desde cero: se analiza, se compila a opcodes, se ejecuta, se envía la salida y se libera la memoria (modelo share-nothing). OPcache permite reutilizar los opcodes entre peticiones.

    Los datos llegan en las superglobales $_POST y $_GET; en las prácticas se leyeron con filter_input(). La sesión se abre con session_start() y se guarda en $_SESSION, y la cookie se protege con HttpOnly y SameSite.

    JSP: ciclo de vida, EL y JSTL

    Un JSP se traduce a un servlet .java, se compila a .class y se instancia una sola vez; después cada petición se atiende en _jspService() sobre la misma instancia. Las fases son: traducción, compilación, instanciación, jspInit(), _jspService() y jspDestroy().

    Para mostrar datos se usan el lenguaje de expresiones EL (${sessionScope.usuario.nombre}) y las etiquetas JSTL como <c:out>, <c:forEach>, <c:if> y <c:redirect>. Tomcat no incluye JSTL, por lo que los .jar van en WEB-INF/lib, y el descriptor WEB-INF/web.xml configura la codificación, el archivo de bienvenida y la sesión.

    Seguridad básica: validación, XSS y patrón PRG
    • Validar en el servidor: la validación del navegador se puede saltar, por eso el formulario se probó con novalidate y el servidor respondió con sus propios errores.
    • Evitar XSS: toda salida se escapa con htmlspecialchars() en PHP y con <c:out> en JSP.
    • Aceptar solo POST: cualquier otro método recibe 405.
    • Patrón PRG (Post/Redirect/Get): tras un POST válido se redirige con 302 para que recargar la página no reenvíe el formulario.

    3. Reflexión: ¿Qué aprendí? y ¿Cómo aprendí?

    ¿Qué aprendí?

    Aprendí cómo se atiende una petición en el servidor y la diferencia entre PHP y JSP: PHP ejecuta el script desde cero en cada petición, mientras que un JSP se traduce a un servlet, se compila y se instancia una sola vez. Lo comprobé en la carpeta work de Tomcat y en el log con jspInit(). También entendí que HTTP no guarda estado y que la sesión con su cookie lo resuelve, que el servidor debe validar siempre los datos, que la salida se escapa para evitar XSS y que el patrón PRG con un 302 evita reenvíos del formulario.

    ¿Cómo aprendí?

    En la hora de teoría se explicaron la arquitectura cliente-servidor, los servidores y el ciclo de vida de PHP y JSP. En la hora de práctica instalé XAMPP y Tomcat y tuve que resolver problemas reales: el puerto 80 ocupado por un servicio de Windows, que resolví pasando Apache al 8081, y el Java 8 incompatible con Tomcat 10.1, que resolví instalando JDK 25. También tuve que colocar los .jar de JSTL en el Tomcat correcto. Probé cada caso con el navegador, DevTools y curl, y revisé los logs. En la práctica grupal trabajamos con un repositorio de GitHub: Edgar desarrolló la aplicación PHP y yo la aplicación JSP y la matriz comparativa.
