    Un framework ya trae la estructura del proyecto, el enrutamiento y el acceso a la base de datos, de modo que el desarrollador se concentra en la lógica de su aplicación.

    Gestores de bases de datos
    • Relacionales (SQL): SQLite, MySQL, MariaDB, PostgreSQL, Microsoft SQL Server y Oracle.
    • No relacionales (NoSQL): MongoDB y Cassandra.

    SQLite guarda toda la base en un solo archivo y no necesita un servidor, por eso es el gestor que Django usa por defecto y el que se empleó en la práctica.

    Arquitectura cliente/servidor multicapa (MPA)

    La arquitectura en capas es una técnica del lado del servidor que se usa para separar un sistema muy complejo. En una aplicación de varias páginas (MPA) el cliente (navegador) solo pide páginas y las capas del servidor se reparten el trabajo:

    Capas de la arquitectura multicapa
    CapaFunción
    PresentaciónLo que se muestra al usuario (HTML y plantillas)
    NegocioLas reglas y la lógica de la aplicación
    DatosEl acceso a la información
    Base de datosDonde se almacena la información
    Arquitectura hexagonal (puertos y adaptadores)

    En la arquitectura hexagonal el dominio (entidades, repositorios y casos de uso) está en el centro y no depende de la tecnología. Alrededor están la capa de aplicación y la de infraestructura, y la comunicación con el exterior se hace mediante adaptadores:

    • Adaptadores primarios (los que llaman a la aplicación): controladores HTTP, endpoints de la API REST y la línea de comandos.
    • Adaptadores secundarios (los que la aplicación usa): la base de datos SQL, un sistema de mensajería como RabbitMQ y un servicio de correo.
    Introducción a Django: MTV, proyecto y app

    Django es un framework web de Python que sigue el patrón MTV (Model-Template-View). Equivale al MVC clásico así: el Model es el modelo, el Template es lo que en MVC es la vista, y la View de Django cumple el papel del controlador.

    Elementos de un proyecto Django
    ElementoFunción
    venvEntorno virtual que aísla las dependencias del proyecto
    manage.pyOrquesta los comandos: runserver, makemigrations, migrate, check, test
    startprojectCrea el proyecto con settings.py y el urls.py principal
    startappCrea una app, que se registra en INSTALLED_APPS
    URLs y vistas: FBV y CBV

    Las rutas se definen con path() en urls.py. Cada app tiene su propio archivo y el del proyecto lo incluye con include(), lo que desacopla las apps. Cada ruta lleva un name para resolverla en las plantillas con {% url 'nombre' %} en vez de escribir la dirección a mano.

    Una FBV (vista basada en función) recibe el request y devuelve una respuesta con render(). Una CBV (vista basada en clase), como ListView o DetailView, reutiliza el comportamiento de Django y se personaliza con métodos como get_queryset() y get_context_data(). En las dos, la vista arma el contexto y la lógica de negocio se delega al modelo.

    Plantillas: herencia, bloques, etiquetas y filtros

    Una plantilla base (base.html) define la estructura común con {% block %} y las demás plantillas la heredan con {% extends %} y rellenan los bloques. Las etiquetas (tags) controlan la lógica: {% for %} con {% empty %}, {% if %}, {% include %} y {% url %}. Los filtros transforman un valor al mostrarlo, como title, upper, date y truncatechars. Django también permite crear filtros y etiquetas propios.

    Modelos, ORM, migraciones y consultas

    Un modelo es una clase de Python que representa una tabla, y el ORM permite consultar la base sin escribir SQL. Los tipos de campo (CharField, TextField, DecimalField, PositiveIntegerField, DateField, BooleanField) definen las columnas. Los cambios del modelo se aplican con makemigrations y migrate.

    Las consultas se hacen con objects.all(), filter(), exclude() y Q. Los QuerySets son lazy: no consultan la base hasta que se evalúan (por ejemplo con list() o count()).

    Fixtures, admin de Django y trabajo colaborativo con Git

    Un fixture es un archivo JSON con datos de ejemplo que se carga con python manage.py loaddata, lo que permite que todo el equipo tenga la misma base de datos sin subir db.sqlite3. El admin de Django se configura registrando el modelo con list_display, list_filter y search_fields. Para trabajar en equipo cada integrante usa su propia rama y sus cambios se integran en main con pull requests.

    Uso responsable de herramientas de IA

    La regla del laboratorio pide escribir manualmente el 75% de la configuración MTV, las vistas y las plantillas, y registrar cada uso de IA con el comentario # IA: [problema] → Solución manual: [explicación].     3. Reflexión: ¿Qué aprendí? y ¿Cómo aprendí?

    ¿Qué aprendí?

    Aprendí cómo se organiza una aplicación Django con el patrón MTV: el proyecto con su urls.py principal, las apps con sus propias rutas, las vistas FBV y CBV, las plantillas con herencia y los modelos con el ORM. Entendí que las vistas deben armar el contexto y que la lógica de las consultas se guarda en el QuerySet del modelo, que las migraciones son las que crean las tablas y que los QuerySets son lazy. También vi que cuando falta algo, Django muestra el error exacto (TemplateDoesNotExist, 404 o no such table) y que conviene leerlo antes de cambiar el código.

    ¿Cómo aprendí?

    En la hora de teoría se explicaron las arquitecturas multicapa y hexagonal, los lenguajes y frameworks de backend, los gestores de bases de datos y los fundamentos de Django. En la hora de práctica seguí los cinco pasos de la guía y los versioné con un commit por paso. Provoqué a propósito los errores de plantilla faltante y de tabla sin migrar para entender su causa, y luego los resolví creando las plantillas y ejecutando makemigrations y migrate. Al final comprobé el proyecto con las 32 pruebas del test runner. En la práctica grupal trabajé con Edgar en ramas separadas de un mismo repositorio: él armó el proyecto, las rutas y las vistas, y yo el modelo, el admin, el fixture de datos, las plantillas y el README, de modo que las partes se integraron con pull requests.
